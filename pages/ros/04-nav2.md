# Nav2

> Status: 🔴 not started

## Concept

Nav2 (the ROS2 Navigation Stack) is the standard answer to "how does a mobile robot get from A to B
autonomously" — a layered system of costmaps (where obstacles are), planners (what path to take), controllers
(how to follow that path moment-to-moment), and behavior trees (how to sequence/recover when something goes
wrong). It's the single most commonly referenced navigation system in mobile-robotics interviews.

## Why it matters

Even outside pure navigation roles, Nav2's architecture is a template interviewers use for "design a
[something]-tolerant system" prompts — layered costmaps, pluggable planners/controllers, and behavior-tree
recovery are a genuinely good answer to "how would you make this robust," whether or not the actual system
involves Nav2 at all.

## Must-knows for interviews

- **Costmaps**: 2D grids representing obstacles, typically layered — a static layer (from a known map), an
  obstacle layer (from live sensor data), and an inflation layer (expanding obstacles by the robot's radius so
  the planner doesn't need to reason about robot shape directly). Global costmap (whole known map) vs local
  costmap (a window around the robot, updated faster) is a common distinction to know.
- **Global vs local planning**: a global planner computes a path across the whole known map (e.g. A*,
  Dijkstra); a local controller (formerly "local planner") follows that path while reacting to live sensor
  data at a much higher rate (e.g. DWB, Regulated Pure Pursuit). Know *why* this split exists: global planning
  is too slow to re-run every control cycle, local control can't see far enough ahead to avoid committing to a
  bad overall route.
- **Behavior trees**: Nav2 uses BTs (not state machines) to sequence navigation behaviors and recoveries
  (compute path → follow path → if stuck, clear costmap / back up / spin / retry). Know the basic BT node
  types: sequence (all children must succeed, in order), selector/fallback (try children until one succeeds),
  and how this composability is the actual advantage over a hand-rolled state machine.
- **Recovery behaviors**: what happens when the robot gets stuck — clearing costmaps (discard possibly-stale
  obstacle data), backing up, spinning in place to re-scan surroundings. This is frequently where "how robust
  is this system really" interview discussions land.
